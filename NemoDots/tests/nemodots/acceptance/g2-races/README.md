## What is real

## Two staleness paths (finding: the closure pre-empts the commit)

ARCH 5.2 step 4 moves live intents `proposed|admitted` to `blocked(stale_version)` as soon as a change is REGISTERED, so a commit-stage re-validation never decides those cases. The suite therefore keeps two kinds of test apart:

- unregistered change (`register: false`): only the commit transaction's own re-validation can refuse. Tests require the commit-stage Authorization row, with the live revision of the changed key above the recorded one in `checked_vector`, an unchanged target version and value, and `actionRows` 0. This covers target, non-target cited source, and inherited-only (snapshot vector) premises, before the commit and inside the `before_lock` and `after_preliminary_read` barriers.
- registered change: the closure path. Accepted outcome: the intent is `blocked(stale_version)`, a later commit throws `DispatchFenceError` (ARCH 5.1 step 2) or returns the blocked intent, and an `ledger.invalidation_events` row names the intent. The commit-stage row is not required there.

After: it arms the crash before `commit()`, because `actions/commit.ts` fires that barrier at the end of `commit()`, after the transaction has committed. ## Oracle id audit and tightening (2026-10-18)

Method: for each frozen ADM, LS or SW id, compare the oracle case's steps and `expected` (every `anyOf` branch included) with the test. An id goes into a title only when that test runs the case's setup and asserts all of its expected fields; extra assertions are allowed. A test that accepts an outcome the oracle does not allow, or leaves out an expected field, is not named.

Lead ruling 2026-10-18: tests that were looser than the oracle are tightened to it, and nothing is loosened. Where the oracle allows several outcomes, one complete branch must hold for every intent of the case, never a mix. A step the oracle does not mark as throwing must not throw. `ADM-17` realizes `age_health` by registering a 121 s old health revision before the proposal. `ADM-20` realizes `mutate_redis_unobserved` by planting a key in the namespace that nothing registers. The SW `recoveryKinds` are compared with the ROUTING kinds recorded for the mission (`repair_scheduled`, `replan_scheduled`, `postcondition_scheduled`, `repair_coalesced`). Bookkeeping kinds (`attempt_aborted`, `intent_blocked`, `branch_preserved`, `invalidation_resolved`) are not routing decisions.

Not named, and why:

- ADM-03b. The replacement is not registered at that step, so the test asserts `stale_pending_observation` (lead ruling). The frozen row says `stale_version`, so the id stays unnamed until the oracle is revised (proposal 3 above).
- ADM-08. The step cannot be reached (review note below).
- SW-1 and SW-3. The oracle's acting lineage `T_parent -> T_act` cannot be realized (review note below). G2-16a and G2-16b assert every other SW field.
- SW-2. No test runs it yet. It waits on the production `SelfWriteIntentPort` adapter.

### Separate-review note: ADM-08 (needs a ruling; the frozen oracle is unchanged)

- Why the step cannot be reached: the case registers the change to IA's key (`advance ... register: true`) before the hooked commit of IA. Registration runs the closure, which moves IA from admitted to `blocked(stale_version)` (ARCH 5.2 step 4). Committing a blocked intent throws before taking any lock (ARCH 5.1 step 2). So `after_lock_before_commit` is never reached, and `during: commit IB` never runs while IA holds its locks.
- Before: `advance(routing.inventory_source, register: true)`, then `hooked(after_lock_before_commit, commit IA, during: [commit IB])`. Expected IA `blocked(stale_version)`, IB committed, `nonBlockingWithinMs` 2000.
- After (proposed): `advance(routing.inventory_source, register: false)`, then the same hooked step. Expected IA blocked with the commit-stage Authorization row (`stale_pending_observation`, as for ADM-01b and 03b), IB committed with admission and commit rows, `nonBlockingWithinMs` 2000, `actionRows` 1. This keeps what the case is about: a parked commit on one resource never delays another resource.

### Separate-review note: SW-1 and SW-3 acting lineage (needs a ruling)

- Why the lineage cannot be realized: a delegated child's capabilities are `ROLE_CAPABILITIES[role]` intersected with the parent's (ARCH 7, enforced by `coordinator/publish.ts#delegate`). Only specialists hold `propose_config_change`, and specialists may delegate verifiers only (D5). A parent of a proposing task therefore cannot exist. The attempt (investigator parent delegating a database_specialist) fails with `capability_denied`, which is correct behaviour.
- Before: `actingLineageTaskIds: ['T_parent', 'T_act']`.
- After (proposed): `['T_act', 'T_ver']`, where T_act is the root specialist that proposes X and T_ver is a verifier T_act delegated before the commit (it inherits T_act's vector). The property tested stays the same: the acting branch and its descendants are kept (SW-1) or invalidated (SW-3).
