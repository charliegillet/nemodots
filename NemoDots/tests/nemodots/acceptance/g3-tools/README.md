## PENDING revision bundle (acceptance-v4 / oracle-v4): CONFIRMED, to apply in the g3-g7 run

Status: prepared 2026-10-18. The integration adversary independently CONFIRMED all four items (none loosens a check), with conditions that become part of the change:

- Items 2 and 3, non-vacuity: "registers nothing" counts only if the composition is started, so each case first asserts that the page-revision hook is installed (`interception/active-policy.ts#getInterceptionHooks().pageRevision` is defined). The adversary's TP-70b is the positive control: the same composed hook registers incident-turn writes.
- Item 4: (a) the receipt is superseded through the real ledger (a new revision of the same source is registered) and its status is asserted `superseded`, with no hand edits to the vector or the receipt row; (b) "before any effect" means zero `sendMail` calls on both handles and no `mcp_actions` claim row; (c) the current-receipt control runs in the same world and on the reconnected handle.
- Item 1 was checked against `sandbox/readers.ts#normalizeMetrics` and ARCHITECTURE 9.4. It is applied as part of the g3-g7 run: the frozen part with a re-freeze (new hashes and a contract revision-log row), the g3 parts as ordinary verifier test corrections. Nothing is loosened: each correction makes a case assert what the current contract says, and item 4 adds coverage.

1. **`oracle/ledger.ts` LG-12 (frozen; opaque input only).**
   - Before: the `m1` registration uses `normalizedValue: { errorClasses: [], cacheHitDecile: 9, errorRateDecile: 0 }`.
   - After: `normalizedValue: { errorClasses: [], cacheDecodeError: null }`. Expectations unchanged.
   - Rationale: ARCHITECTURE 9.4, revised 2026-10-18. `checkout.metrics` digests only the error classes seen and `cacheDecodeError`; the deciles moved with ordinary traffic and minted false revisions (`tests/nemodots/integration/sandbox/observed-stability.test.ts`, EVALUATION.md section 12). The ledger does not validate observed shapes, so the case passes either way; the change only stops the oracle showing a dead shape as if it were the contract.
2. **g3-08 `[TP3.1][M4]` owner page routes (not frozen).**
   - Before: after an owner create it expects a `opendots.page/<id>` trace in the ledger (`tablesContaining(...)` not empty), and it sends DELETE without a body or content type.
   - After: it asserts that owner create, patch and delete register no `opendots.page/<id>` ledger source. It sends DELETE with `Content-Type: application/json`. The upstream CAS assertions (201, 200, stale 409 with the page unchanged, 200 on delete) are unchanged. New title: "owner create, patch and delete keep upstream CAS and register nothing in the ledger".
   - Rationale: TOOL_COVERAGE M4 (Dot-turn scope ruling): "owner routes are out of the model's reach. The `Pages` revision hook runs but registers nothing". The upstream `/api` middleware refuses any non-GET request without a JSON content type with 415 (`src/server/app.ts:94-98`). The old case would have hit that once its first assertion was fixed.
3. **g3-08 `[TP3.1][M3]` reviewed-page route (not frozen).**
   - Before: after saves by an ordinary Dot's thread it expects a `opendots.page/<id>` trace in the ledger.
   - After: the idempotency assertions (201, the same id on replay, 409 for a different draft) are unchanged, and it asserts that no `opendots.page/<id>` ledger source exists. New title ends "...; the write registers nothing in the ledger".
   - Rationale: TOOL_COVERAGE M3: "the write registers nothing (owner and ordinary-Dot writes are never registered; only incident-Dot turns' page revisions are)".
4. **g3-05 `[TP3.6][M10]` fresh-evidence callback (not frozen).**
   - Before: any non-NULL stored `dependency_vector` counts as bound evidence, so a page edit must give 409 `stale_evidence`.
   - After, part one: for the ordinary Dot it asserts the product's documented value, an empty vector `[]`. The callback after the page edit then runs the stored request exactly once (200), also through a reconnected handle.
   - After, part two (added coverage): the 409 `stale_evidence` path is tested with a NON-empty bound vector. The verifier binds a vector naming a current receipt to the approval, then supersedes that receipt through the real ledger (a new revision of the same source, status asserted `superseded`). It expects 409 `stale_evidence` with zero `sendMail` calls on both handles and no `mcp_actions` claim row, directly and after a reconnect. Control, in the same world and on the reconnected handle: with the receipt current, the callback runs once. The one-time setup write of the bound vector is accepted by the reviewer: it does not touch the payload hash, which covers connection, tool and arguments only. After setup the vector and the receipt row are never edited; the vector goes stale only through the ledger. No product path produces a runnable approval with a non-empty vector (ordinary Dots store `[]`, incident Dots never create approvals), so this case tests M10 as defence in depth.
   - Rationale: TOOL_COVERAGE M9: "in the product the vector is `[]`, except after an incident Dot's page reads". M10: the callback checks "the bound vector (409 `stale_evidence`)". The old case read `[]` as bound evidence, which is why it saw 200 where it expected 409.
