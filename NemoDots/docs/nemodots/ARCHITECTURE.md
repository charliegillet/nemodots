# NemoDots architecture (v1, revision 2 after adversarial review)

Author: systems architect (Claude Code workflow subagent, Fable 5.1), 2026-10-17. Inputs: the Phase 0 audits under `docs/nemodots/audit/`, the OpenDots source they cite (every `file:line` below was checked against the tree on this date), `LEAD_NOTES.md` (which wins over `BUILD_PROMPT.md`), and the three devil's-advocate reviews recorded in section 14. This document wins over the audits where it makes a decision; `CONTRACTS.md` is normative for field names and enums.

Tagline: when evidence changes, the team adapts. The mechanism: every model call, output, delegation and controlled action carries the exact source revisions it rests on; the same PostgreSQL transaction that advances a source revision is the one that can reject a dependent commit; recovery re-reads instead of replaying.

Companion documents: `CONTRACTS.md` (typed contracts v1), `TOOL_COVERAGE.md` (every OpenDots tool/execution path and its treatment), `DEPENDENCIES.md` (packages, services, task and evidence dependencies), `IMPLEMENTATION_STATUS.md` (one reviewed task contract per package).

## 4. The narrow enforceable guarantee

**Guarantee G1 (controlled commits).** A controlled configuration mutation of the checkout commits only if, inside one PostgreSQL transaction that first locks the intent row and then holds `FOR UPDATE` row locks on every controlled source in the intent's dependency vector and on the target (stable key order, collection row first when present), all of the following hold: the intent is `admitted` and the committing dispatcher's fence equals the stored dispatch fence with an unexpired dispatcher lease; every required source's current version equals the version recorded in the intent's supporting receipts; every supporting receipt is `supported` and its freshness (`lastConfirmedAt`) satisfies the policy's `maxAgeMs`; the target's current version equals `expectedTargetVersion`; the author attempt's fencing token was valid when the proposal was published; the mission generation is unchanged and the mission row is share-locked; the actor capability permits the action; the policy version matches. The mutation, the version advance, the `config_versions` row (with `caused_by_action_id` and before/after digests), the `result_receipts` row, the intent transition and the outbox event are written in the same transaction. The admission transaction (section 5.1) runs the same predicates earlier; commit **re-executes every one of them** under lock (finding C4).

**Guarantee G2 (publication).** A task output, handoff, child enqueue, finding or model-call record is accepted only if `SupportValidator.assertCurrent` passes inside the publishing transaction with the controlled rows of its vector locked `FOR SHARE` (so a concurrent writer's `FOR UPDATE` waits until the publication commits, finding C9), and the publishing attempt's fence, generation and mission share-lock hold.

**Guarantee G3 (immediate staleness).** When a controlled source version advances, every receipt recording the old version is non-current from that commit on, before any watcher runs, because G1/G2 compare recorded versions with the live `config_entries.version`/`config_collection.version` under lock. A pending replacement observation is not permission: the comparison fails closed with reason `stale_pending_observation`.

**Limits (stated in UI and report).**

- G1 covers controlled sources only (`checkout.config/<key>` members and the `checkout.config` membership collection). Observed sources (health, metrics, Redis stats, recent orders, inventory, page snapshots) have ledger-assigned revisions: dependents are invalidated when a newer observation differs, and admission requires a confirmation younger than `maxAgeMs`, but a change the watcher has not observed cannot be detected. For observed sources the property is **freshness-at-admission** (and, for the Redis effect, freshness-at-dispatch); `actions/README.md` states the exact windows.
- `flush_cache_namespace` is an external effect. The PostgreSQL CAS in `claimDispatch` (target version unchanged) and the Lua script (fence not newer, per-action marker absent) make the effect fail closed and idempotent per action; a Redis failure between effect and acknowledgement leaves `outcome_unknown` until `reconcile` reads the marker back. The guarantee is "no second effect without a new authorization, no effect under an obsolete fence", not atomicity with the commit.
- Nothing outside the enumerated toolset is covered. OpenDots tools for incident Dots (`NEMODOTS_INCIDENT_DOT_IDS`) are disabled or policy-wrapped (TOOL_COVERAGE.md); with that list empty the defence-in-depth rows are inactive and upstream behaviour is unchanged.
- Compensation is optional and implemented only for `set_config`; it is itself an intent that must pass G1 against the current version. Irreversible effects are never shown as undone.
- The single owner (`OWNER_ID`) is the only identity; there is no multi-tenant isolation beyond `environment`/`resource` scoping.

## 5. Serialization order: invalidation versus commit

### 5.1 Lock protocol (all writers of controlled sources)

Three writers advance controlled versions: the action commit, the injector, the owner manual edit. All go through `sandbox/version-authority.ts::advanceConfig(client, {key, value, expectedVersion, causedBy})`, the single writer of `config_entries`, and all use this statement order. Isolation is `READ COMMITTED`; row locks make check-then-write safe (the concurrency adversary proves equivalence under `SERIALIZABLE`).

1. `BEGIN`.
2. (actions only) `SELECT ... FROM coordinator.action_intents WHERE id=$1 FOR UPDATE`. If `status` is already `committed | dispatched | verified` return the stored `ResultReceipt` and **write nothing** (duplicate delivery, finding C2). If `status` is not `admitted`, or `dispatch_fence <> $f`, or `dispatcher_lease_expires_at <= now()`, throw `DispatchFenceError` (nothing written; the intent stays claimable).
3. (actions only) `SELECT generation FROM coordinator.missions WHERE id=$m FOR SHARE` and compare with the intent's generation (finding C12).
4. If the write inserts or deletes a key, or the vector contains the collection: `SELECT version FROM checkout.config_collection FOR UPDATE` (collection row **first**).
5. `SELECT key, version FROM checkout.config_entries WHERE key = ANY($keys) ORDER BY key FOR UPDATE`, `$keys` = sorted union of the vector's member keys and the target. The injector and owner edit lock the target only (plus the collection row when inserting/deleting).
6. (actions) validate every G1 predicate against the locked rows and `ledger.observation_receipts` (`FOR SHARE`) + `ledger.receipt_confirmations`; on failure write an `Authorization(blocked, reason)` row, move the intent `admitted → blocked`, `COMMIT`, return.
7. `UPDATE checkout.config_entries SET value=$v, version=version+1, caused_by_action_id=$a, caused_by_actor=$actor, updated_at=now() WHERE key=$k AND version=$expected` (row count must be 1, else `stale_version`).
8. `INSERT INTO checkout.config_versions(key, version, value, before_digest, after_digest, caused_by_action_id, caused_by_actor, at)`; if a key was inserted/deleted, `UPDATE checkout.config_collection SET version=version+1`.
9. (actions) `INSERT coordinator.result_receipts`, `UPDATE action_intents SET status='committed' ... WHERE id=$1 AND status='admitted' AND dispatch_fence=$f`, `INSERT coordinator.outbox`, `pg_advisory_xact_lock(hashtext('nemodots_events'))` + `INSERT coordinator.events`.
10. `SELECT pg_notify('nemodots_source_changed', payload)`; `COMMIT`.

Because every writer locks the collection row (when touched) before member rows and member rows in key order, overlapping writers serialize without deadlock; whichever commits first advances the version and the other fails its `version = expected` predicate with `stale_version`. Non-overlapping keys do not block each other (per-resource versions, not a mission epoch). A value update never touches the collection row, so the benign B1 change leaves every member and collection receipt current (finding C1/D1).

**Admission transaction** (`actions/admit.ts`, `proposed → admitted`): lock the intent row `FOR UPDATE`, mission `FOR SHARE`, controlled rows `FOR SHARE`, run the same predicates, claim the dispatch lease (`dispatch_fence = nextval(...)`, `dispatcher_lease_expires_at = now() + NEMODOTS_DISPATCH_LEASE_MS`), write `Authorization(admitted)`, commit. `admitted` is durable; between admission and commit the predicates may become false, which is exactly what the commit transaction detects (TEST_PROMPT gate-2 items 4 and 15). An `admitted` intent whose dispatcher lease expired is re-claimable by any dispatcher (`claimDispatch` CAS on `status='admitted' AND dispatcher_lease_expires_at <= now()`); the old dispatcher's commit fails at step 2. Admission runs from the outbox after `action.proposed`, no earlier than `mission.admission.minAgeMs` after the proposal (default 0; recorded on the mission; see section 11 and finding D6).

### 5.2 Receipt registration and closure materialization

`ledger.registerObservation` (watcher, `observe_source`, probe, postcondition) runs in one transaction:

1. `INSERT INTO ledger.sources ... ON CONFLICT DO NOTHING`, then `SELECT ... FROM ledger.sources WHERE id=$1 FOR UPDATE` (serializes concurrent registrations of one source, finding C8).
2. Read the current receipt under that lock. For controlled sources the revision is the authority's version read in the same transaction (`FOR SHARE` on the config row); registering a revision lower than the current receipt's is refused (`stale_observation_rejected`). For observed sources: if the normalized digest equals the current receipt's, **no new revision is minted**; a `ledger.receipt_confirmations(receipt_id, confirmed_at, provenance)` row is appended and the current receipt is returned (findings I2/D3). Otherwise the revision is `current + 1`.
3. Insert the new receipt `supported`; mark the prior current receipt `superseded` with a `receipt_transitions` row and a CAS on `(status, status_version)`.
4. Compute the closure: a bounded recursive CTE over `ledger.dependency_edges` (`evidence` and `inheritance` edges only, never `scheduling`), marking affected attempts `invalidated`, outputs `unusable`, live intents `blocked(stale_version)` (through the actions CAS, so an in-flight commit that holds the row lock is serialized before or after this transaction, never interleaved), tasks `invalidated`. Depth cap 64, node cap 10 000.
5. Insert one `ledger.invalidation_events` row (global) and one `coordinator.events('invalidation.recorded')` per affected mission containing **only that mission's subset** of affected/preserved (finding I10); `NOTIFY nemodots_outbox`.

If the cap is exceeded the registration transaction is **not** abandoned forever (finding C14): the closure is aborted, and in a fresh transaction the watcher pauses the affected missions with reason `closure_cap_exceeded`, records a coarse `InvalidationEvent` (affected = every non-terminal attempt/intent of those missions, `closure.capped = true`), then registers the receipt with the closure skipped. The source stays observable.

A `SupportError` raised at publication time (G2) moves the publishing attempt to `invalidated` (not `failed`), with a synthetic `InvalidationEvent` (reason `publication_rejected`) and a `repair_scheduled` recovery event, so the repair path with fresh reads and the invalidation summary is used rather than a blind retry (finding C13).

### 5.3 External effects (Redis)

`flush_cache_namespace` is committed in PostgreSQL (status `committed`, desired state recorded) and then dispatched:

1. `claimDispatch`: `UPDATE action_intents SET dispatch_fence = nextval(...), dispatcher_lease_expires_at = ... WHERE id=$1 AND status='committed' AND (SELECT version FROM checkout.config_entries WHERE key='cache.namespace') = committed_target_version`. Row count 0 with a changed version → `failed(dispatch_fence_invalid)` (the authority moved; finding C11). The flush target's authority is `checkout.config_entries['cache.namespace'].version`; `expectedTargetVersion` for a flush is that version.
2. One Lua script, atomic in Redis: `SET <prefix>:effect:<actionId> <dispatchFence> NX EX <reconcileHorizon>`; if it already existed return `already_applied` without touching keys (finding C3). Then compare `<prefix>:fence:<namespaceResource>` with the committed version: if the fence is **strictly newer** return `fence_newer` (no effect). Otherwise `SCAN`/`UNLINK` the namespace, `SET fence = version`, return `applied` with the deleted count.
3. Record `dispatched → verified` with the readback, or `outcome_unknown` if the call threw or timed out. `reconcile` reads the effect marker: present → the effect happened once (settle `verified`), absent → it did not (settle `failed(effect_not_applied)`, re-dispatchable only through a new authorization). The readback count alone is never treated as proof of effect.

### 5.4 Self-writes (`causedByActionId`) classified against history

A successful commit records `caused_by_action_id`, `before_digest` and `after_digest` in `checkout.config_versions` (the history) and on `config_entries` (the head). The watcher classifies by walking the history, not by looking at the head only (finding C7): when it observes head version `r+n` while the ledger's current receipt is `r`, it reads `config_versions` rows `r+1..r+n` in order and, for each row with a `caused_by_action_id`, settles that intent: `after_digest == expected_after_digest` → `committed → verified` (postcondition `kind: 'history'`), else `failed(postcondition_mismatch)`. The head receipt it registers carries `provenance.selfWrite` derived from the **last** row (`verified`, `mismatch` or `none`).

Recovery consequences:

- `verified` (last row is a verified self-write): the acting lineage (proposing attempt, its task, ancestors awaiting the result) is not invalidated; a `postcondition` attempt with fresh scoped reads is enqueued. Attempts in other branches that read the old revision are invalidated (their premise changed); their repairs are coalesced behind the postcondition verification (`repair_coalesced`).
- `mismatch`: full invalidation; intent `failed(postcondition_mismatch)`.
- `none` (injector/owner/external write last): full invalidation; any committed set_config on the same key whose own row was verified earlier in the walk is `verified`; one whose row is not in the walk (impossible by construction, since every commit writes a row) would be `failed(superseded_before_verification)`.

The marker is server-authored inside the commit transaction. Tool inputs have no field for it (`propose_action` payload is strict); the `BEFORE UPDATE` trigger on `config_entries` nulls `caused_by_action_id` unless `current_user = 'nemodots_app'`. This blocks the injector, checkout, verifier **and admin** roles; the app role is trusted code (finding I14), so integration tests that exercise self-writes must use the app URL from `test-db.ts`.

## 6. Leases and fences

| Lifecycle | Holder                                            | Token                                                                           | Granted                                                                                                                                    | Renewed                                                                                                 | Checked                                                                                                                                                                                                                                                                                  |
| --------- | ------------------------------------------------- | ------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Authoring | worker running a `TaskAttempt`                    | `fencingToken = nextval(task.fence_seq)` (monotonic per task), `leaseExpiresAt` | `claimAttempt` CAS: task `runnable → leased → running`                                                                                     | heartbeat every `NEMODOTS_LEASE_MS/3`, `UPDATE ... WHERE fencing_token=$t AND lease_expires_at > now()` | every publication (`publishOutput`, `delegate`, `publishFinding`, `propose`, `recordModelCall`) runs `WHERE attempt_id=$a AND fencing_token=$t AND status='running' AND generation=$g` after `SELECT ... missions FOR SHARE`; row count 0 → `FenceError`, nothing written, worker aborts |
| Dispatch  | dispatcher admitting/committing an `ActionIntent` | `dispatchFence = nextval(intent.dispatch_seq)`, `dispatcherLeaseExpiresAt`      | `claimDispatch` CAS on `status='proposed'` (admission) or `status='admitted' AND lease expired` (re-claim) or `status='committed'` (flush) | heartbeat while the dispatcher works                                                                    | commit/dispatch/reconcile statements include `AND dispatch_fence=$f AND dispatcher_lease_expires_at > now()`                                                                                                                                                                             |

Takeover: a reaper marks attempts with expired leases `expired`, bumps `fence_seq`, and makes the task `runnable`; the old worker's next fenced statement fails. The author's fence is validated at proposal publication; a proposal published by a still-valid author remains valid for dispatch after the author completes. An expired author cannot publish; an expired dispatcher cannot admit or commit.

Telemetry exception (finding C16): a model call that completed on Crusoe while the lease was lost is still stored as an unfenced `ledger.inference_attempts` row with `outcome='orphaned_fence'` (tokens, timings, no evidence edges, no output reuse) so cost accounting is complete; only the fenced `ModelCallRecord`/edges write is rejected.

Run generation: `missions.generation` increments on cancel; every attempt and intent records its generation and every fenced statement includes `AND generation = $g` after share-locking the mission row, so a cancel (`UPDATE missions ... generation=g+1`) waits for in-flight publications/commits and then rejects later ones. Effects committed before the cancel's lock are listed in the cancellation record (`committedEffects`).

## 7. State machines

### 7.1 Mission

`created → running → awaiting_acceptance → succeeded`; `running ↔ paused`; `running | paused | awaiting_acceptance → cancelled`; `running | awaiting_acceptance → failed`; `created → blocked_provider → created`. `succeeded` requires an acceptance probe receipt with `verdict: pass` **and zero open invalidations**. An invalidation is **open** while any attempt in its `affected` set is non-terminal or terminal without a published repair/postcondition output, or any affected intent is not `blocked | failed | cancelled | verified`; it closes when the coordinator records `invalidation_resolved` (finding D9). Transitions are CAS on `(id, status, transition_version)`.

### 7.2 Task

```text
pending ──prereqs done──▶ runnable ──claim──▶ leased ──start──▶ running ──publish──▶ succeeded
   │                         ▲                                   │  │ └─children pending─▶ waiting ──all children done──▶ running
   │                         │                                   │  └─error/budget────────▶ failed
   │                         └───────repair attempt scheduled────┤
   │                                                             └─invalidation────────▶ invalidated ──schedule──▶ repairing ──▶ runnable
   └── any non-terminal ──cancel──▶ cancelled                    (terminal: succeeded, failed, cancelled)
```

`succeeded` outputs remain `usable` only while their vector is current (G2 re-check on every reuse). The **plan is a scheduling artifact**: tasks record `createdByModelCallId` for provenance but are not evidence dependents of the planner's reads; replanning is triggered only by root-task invalidation or `request_replan` (finding D1).

### 7.3 Attempt

`running → published | failed | aborted | expired | invalidated`. `aborted` is best-effort cancellation of in-flight work when the readset is invalidated or the mission is paused/cancelled; the state is written before the abort signal fires so a late publication is rejected by the fence check, not by timing. A `SupportError` at publication yields `invalidated` (section 5.2).

### 7.4 Action intent

`proposed → admitted → committed → dispatched → verified`; `proposed | admitted → blocked(reason)`; `committed | dispatched → outcome_unknown → verified | failed`; `admitted | committed → failed(reason)`; `proposed | admitted → cancelled`. `admitted` is durable (section 5.1). For `set_config` there is no `dispatched` hop: `committed → verified` when the watcher's history walk confirms the after-digest, or `failed(postcondition_mismatch | superseded_before_verification)`.

### 7.5 Receipt

`supported → superseded | contested | retracted | expired`; `contested → supported | retracted`. Only `supported` receipts with a sufficiently recent confirmation (where the policy requires one) support admission.

## 8. Event stream

`coordinator.events(id BIGSERIAL PRIMARY KEY, mission_id, kind, payload JSONB, created_at)`. Every inserting transaction takes `pg_advisory_xact_lock(hashtext('nemodots_events'))` immediately before the `INSERT`, so id order equals commit order and `WHERE id > $last` never skips a row (finding C6). `GET /api/nemodots/missions/:id/events` streams `id: <n>\nevent: <kind>\ndata: <json>\n\n`; the server reads `Last-Event-ID` from the header, replays `id > n`, then tails via `LISTEN nemodots_events` with a 2 s poll fallback; heartbeat comments every 15 s. Scope: the mission id in the path; events of other missions are never written (invalidations are emitted per mission with that mission's subset). The client reducer (`src/client/nemodots/mission-events.ts`) is pure: dedupes by id **set** (accepts out-of-order ids defensively), merges a snapshot, exposes `lastEventId = max(id)`. Payloads are a typed discriminated union (CONTRACTS section 8) carrying ids, digests and display fields, never prompts or `control` data.

## 10. Live, fixture and blocked modes

`NEMODOTS_INFERENCE_MODE` is `live` (default), `fixture` or `blocked`. The mission's `mode` is always the **server-resolved** mode; a body `mode` may only equal it or be omitted, otherwise 400 (finding I11).

- **live** requires `OPENAI_API_KEY`, `OPENAI_BASE_URL` and `OPENAI_MODEL` (all three; missing names are reported, never values). No default base URL exists in `src/server/nemodots/**`; health reports `provider.host = new URL(OPENAI_BASE_URL).host` and the live suites assert every request went to that host (finding I1). At bootstrap and on `GET /api/nemodots/health`, `GET /v1/models` must list the configured model. If the provider becomes unreachable, in-flight attempts fail with `provider_unreachable`, the mission moves to `blocked_provider`, badge **BLOCKED: provider**.
- **fixture** requires `NEMODOTS_FIXTURE_PATH`; replays recorded responses keyed by digest(model, system, messages, toolSchemaHash). Missions are stamped `mode: 'fixture'`, badge **FIXTURE**; the evaluation harness refuses to count them as live trials.
- **blocked**: any live requirement missing. Mission creation returns 503 with `missingEnv` names; the page stays usable for past missions, evidence and health, badge **BLOCKED: <names>**.

Intelligence is a separate badge (**Intelligence: configured** or **blocked, conversations unavailable**) and never changes the upstream `setupStatus`.

## 11. The Nemotron team

All runtime reasoning runs on Crusoe. Roles are prompts plus **capability sets that make delegation structurally necessary** (finding D5):

| Role                                                            | Capabilities                                                                                                               | Why delegation happens                                                     |
| --------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| `planner`                                                       | structured output only                                                                                                     | produces 2-6 root tasks from goal + health + membership (no member values) |
| `investigator`                                                  | `observe`, `delegate`, `publish_finding`, `request_replan`                                                                 | cannot propose any action: a repair must be delegated to a specialist      |
| `cache_specialist`, `database_specialist`, `routing_specialist` | `observe`, `delegate` (to `verifier` only), `publish_finding`, `propose_config_change` (+ `propose_cache_flush` for cache) | the only roles that can propose; may delegate a verification child         |
| `verifier`                                                      | `observe`, `publish_finding`                                                                                               | reads and reports after a repair; proposes nothing                         |
| `postcondition`                                                 | `observe`, `publish_finding`                                                                                               | system-created after a verified self-write                                 |

- **Planner** (`nvidia/NVIDIA-Nemotron-3-Super-120B-A12B`, `reasoning_effort: "none"`, strict `json_schema` validated by `contracts/task.ts::PlanSchema`): input is goal, constraints, runbook catalogue, `checkout.health` and the `checkout.config` membership receipt (not member values). Output: root tasks with roles, capability scopes (⊆ role defaults) and causal dependencies. Validation: cycle check, caps, capability subset; one bounded correction turn, then `failed(invalid_plan)`.
- **Workers**: tool loop (`team/worker-loop.ts`) with typed tools whose identity comes from `context.context = AttemptContext` server-side: `observe_source(sourceKey)` (registers or confirms a receipt; adds to the readset), `list_runbooks()`/`read_runbook(id)` (ids resolved through the catalogue map only, never a path join; finding I13), `delegate_task({title, role, question, dependsOn, justification})` (depth ≤ `NEMODOTS_MAX_DEPTH`, breadth ≤ 4, total ≤ `NEMODOTS_MAX_TASKS`, child capability ⊆ parent, except that a specialist delegated by a parent holding `delegate` keeps its role's `propose_*` capabilities: rev3 D5, user-approved 2026-10-18), `get_task_status(taskId)` (same mission only), `wait_for_children()`, `publish_finding({claim, supportingReceiptIds})`, `propose_action({action, payload, supportingReceiptIds, rationale})`, `request_replan(reason)`. At most 12 iterations per attempt, 60 s per inference call, budgets server-side.
- **Provenance at the action boundary** (findings C10/I8): the server-computed `dependencyVector` of an intent is the `snapshot.dependencyVector` of the model call that emitted the `propose_action` tool call (which already contains the readset, inherited vectors and every injected item) ∪ cited receipts, sorted. A cited receipt must be present in that snapshot's vector or in the attempt's readset/inherited vector; a receipt the attempt never saw is `blocked(citation_out_of_scope)`. Receipt ids are therefore citations validated against scope, never authority.
- **Admission timing** (finding D6): `action.proposed` is emitted with `NOTIFY nemodots_action_proposed`; admission is an outbox step that waits at least `mission.admission.minAgeMs` (default 0, set at mission creation and shown in the UI). The demo sets 3 000 ms so a scenario-driven dependent change can land first; the live `changed-evidence` test asserts the honest disjunction (either `blocked(stale_version)` at admission/commit, or a commit followed by the second invalidation and repair) and records which occurred. The deterministic stale-commit proof lives in the integration tests with barriers; `NEMODOTS_TEST_HOOKS` is never set in a run labelled live.
- **Replanning**: an invalidation creates a `repair` attempt for each affected task with the invalidation summary and fresh scoped reads (never the old transcript); the planner is re-invoked only when a root task is invalidated or a worker calls `request_replan`. Preserved branches are untouched. The live assertion for "branch B preserved" is structural: the expected preserved set is computed from recorded readsets/edges (tasks with no evidence or inheritance path from the changed receipt); the test asserts zero new model calls for exactly that set and reports `NOT_MET` when the set is empty instead of forcing it.

Context compiler (`context/compile.ts`) emits exactly one system string laid out as `common instructions + ordered tool schemas` → `stable authorized runbook context` → `role instructions` → `scoped versioned evidence + task + volatile time`. `prefixDigest`/`prefixLength` cover the first three sections; `contextDigest` covers everything; both are stored on the `ModelCallRecord` with every injected receipt id/revision, artifact digest, runbook digest and the tool schema hash. The ordinary layout (evaluation 2×2) interleaves evidence and puts the volatile time first; information content is identical.
