## Method notes

- **Deadlock detector.** `harness.ts` wraps every pool of the world so that SQLSTATE 40P01 and 40001 are recorded _before_ `withTransaction` retries them; a retried deadlock cannot hide. Negative controls (a reversed lock order on raw sessions, in the exact shapes of the C1 tests) prove the detector sees a real 40P01.
- **Non-vacuity rule (added in round 1).** A randomized test must (1) admit its intents BEFORE the writers start, (2) contain pipelines that no writer can invalidate and assert that they commit, (3) where a commit has to hold locks while the writers run, park it at `after_lock_before_commit` and release it only after the writers queue, and (4) assert a lower bound on commits. Round 0 broke all four: the C1 stress, the isolation "12 random races" and the mixed stress each blocked every intent at admission (measured by the reviewer: `{admission:blocked:6}`, `{admission:blocked:12}`, `{admission:blocked:5}`), so their "zero deadlocks / at most one winner" assertions held trivially. They are rewritten. Round 0 also claimed "key deletes" in the C1 stress; no test deleted a key. The new C1 tests delete keys for real.
- **Mutation check of the C1 shapes (scratch copy, not production).** The whole `src/` and `tests/` trees were copied under `.local/review/w5-concurrency-adversary/mut/`, `lockConfigRows` in the copy was changed to take the member rows BEFORE the collection row, and the C1 file was run against the copy. Result: exactly the two new discriminating tests ("member pre-locked", "collection pre-locked") fail; the two round-0 deterministic tests and all three stress runs stay green. That is the proof that round 0 could not detect a reversed commit order and that the new tests can.
- **Doubles, all labelled in `harness.ts` or the test file.** Missions, tasks and attempts are inserted with SQL; the coordinator used by C9, C12 and the mixed stress is the real one wired to the real ledger validator and a ledger writer that stores edges with the ledger's own functions; the watcher's `SourceReaderPort` reads the real authority rows and its `pauseMission` is a SQL double; `onSelfWriteSettled` is wired to the real `settleFromHistory` as the watcher README requires; the observe_source executor (`team/observer.ts`) is the real one over the real ledger with a scripted `SourceReaderPort`, a mission-facts reader and an event sink that delegates to the real sink and can park.
- **Isolation.** `ALTER DATABASE ... SET default_transaction_isolation` before any pool exists runs the production transactions (plain `BEGIN`) at READ COMMITTED, REPEATABLE READ or SERIALIZABLE with no code change.

### CW-1 (low) a mislabelled marker row fails a correct action

- **Command.** `... vitest run --config tests/nemodots/adversarial/concurrency/vitest.config.ts self-write-forgery`
- **Reproduction.** Action A commits `db.pool_max` (history row v2 carries A's id and the expected digest). The trusted application role then writes a history row on `ui.banner_text` that names A as its `caused_by_action_id` (the triggers null the marker for every other role, so nothing but the app role can do this). The watcher walks that key, finds the intent known but for another key, classifies `failed` and calls `onSelfWriteSettled(A, 'failed')`.
- **Expected** (ARCHITECTURE 5.4): an intent is settled from _its own_ row; `after_digest == expected` is `verified`. A's own row is correct, so A must not become `failed`.
- **Actual.** A ends `failed(postcondition_mismatch)`. `settleFromHistory` accepts the verdict without re-checking the intent's own history row. A second test (`a marker row on another key never VERIFIES the intent`) passes: the unsafe direction is closed.
- **Severity.** Low. No input surface reaches it; it is a consequence-if-the-trust-boundary-slips finding.
- **File.** `src/server/nemodots/actions/settle.ts` (`settleFromHistory`, outcome `failed`): look the intent's own `config_versions` row up and refuse `failed` when its digest matches. Not edited.
- **Test form.** `it.fails`: green while the defence is absent; when fixed the test starts failing and must be flipped to `it`.

### CW-2 (medium) isolation levels are equivalent for safety, not for liveness

Raised from low in round 1. ARCHITECTURE 5.1 fixes READ COMMITTED and states that the concurrency adversary proves equivalence under SERIALIZABLE. A call that is _rejected_ is a different outcome from one that is _blocked_, so the statement is false whenever a 40001 survives the retries.

- **Command.** `... vitest run --config tests/nemodots/adversarial/concurrency/vitest.config.ts isolation-levels`
- **Deterministic reproduction (round 1).** The `before_lock` barrier runs inside the real admission / commit transaction after its first statement (so a snapshot exists at the stronger levels) and before the intent row lock. The handler updates the intent row in another session and commits. PostgreSQL itself then raises 40001 ("could not serialize access due to concurrent update") at the `FOR UPDATE` of every attempt at REPEATABLE READ and SERIALIZABLE; at READ COMMITTED the same hook is harmless. Per level, for `admit` and for `commit`:
  - READ COMMITTED: one attempt, no 40001, `admitted` / `committed`.
  - REPEATABLE READ and SERIALIZABLE: exactly 5 attempts (the `withTransaction` default; `commit` passes `maxAttempts: 5` explicitly), five recorded 40001, and the call **rejects with code 40001**. Nothing is decided silently: an `admit` leaves the intent `proposed` with zero Authorizations, a `commit` leaves it `admitted` with no action history row and the value unchanged. After the contention stops the same call decides normally (recoverable).
- **Real contention (round 1 re-derivation, replaces the round-0 number).** `contended commits` (12 intents admitted at one expected version, the winner parked holding the row, 11 competing commits and 4 injector writers queued): in 3 runs of 10 rounds each, READ COMMITTED had 0 retried 40001 and 0 rejected calls; REPEATABLE READ had 204-220 retried 40001 and 0 rejected calls; SERIALIZABLE had 328-348 retried 40001 and **3-4 rejected calls per 10 rounds**, every one a losing `commit` (blocked-at-commit path), each leaving its intent `admitted` and retryable. The shipped test runs 3 rounds, asserts the safety invariants for every outcome, requires exactly one committed winner at READ COMMITTED and "winner committed or PostgreSQL reported a 40001" at the others, and tolerates only 40001 as a rejection.
- **Safety holds in every outcome.** History gapless; the committed action wrote exactly at `expectedTargetVersion + 1`; at most one action wins a version; no 40P01 at any level.
- **Severity.** Medium: a documented statement is false (liveness), the production level (READ COMMITTED) is immune in every run.
- **Dependency.** Either amend ARCHITECTURE 5.1 ("equivalence holds for safety; at REPEATABLE READ and SERIALIZABLE a persistent 40001 surfaces as a rejected call after five attempts, leaving the intent `proposed` / `admitted`") or raise `maxAttempts` for the `blockIntent` paths of `actions/admit.ts` and `actions/commit.ts` and map an exhausted budget to a typed, retryable result. Keep production at READ COMMITTED either way.

### CW-3 (info) residual windows, stated explicitly

**Freshness at admission** (observed sources: `checkout.health`, `redis.stats`, metrics, recent orders, inventory, page snapshots). The guarantee for an observed source is that the receipt is not superseded in the ledger and that `lastConfirmedAt >= now - maxAgeMs` (policy-v1: 120 000 ms for `checkout.health` and `redis.stats`), evaluated with the database clock at admission and again, under the commit locks, at commit. A change of the real world that no watcher or tool has registered cannot be detected. A commit can therefore rest on an observed fact that is no longer true for up to `maxAgeMs` after its last confirmation **plus** the admission-to-commit latency (bounded by the 10 minute intent expiry; the dispatcher lease only bounds who may commit, not for how long the evidence has been unobserved). `c04` pins both halves: the same evidence 1.1 s past its limit between admission and commit is `blocked(evidence_too_old)`, and a world change nobody observed commits (RESIDUAL test). A further, liveness-shaped version of this window is CW-8: while a superseding registration is starved, the new fact stays unregistered until the retry.

**Freshness at dispatch** (the Redis flush). Only the controlled authority is re-checked: `claimDispatch` compares `checkout.config_entries['cache.namespace'].version` with the version the flush was committed at, in the claim's own transaction. `c11` proves it refuses an advance that happens before the dispatch, between the commit and the dispatch (barrier `after_commit_before_dispatch`) and inside the claim transaction's own start (barrier `before_lock`). The window that remains is _claim committed -> script executed_ (milliseconds, plus any Redis stall up to the Redis budget of 5 s): an advance in that window is not seen and the flush of the old namespace runs (RESIDUAL test in `c11`). `redis.stats`, the observed evidence behind a flush, is not re-read at dispatch; its age is bounded by `maxAgeMs` at commit and by the intent expiry. The Redis fence orders flushes among themselves only and is never consulted for permission. The flush payload namespace is validated for shape only (`^[a-z0-9-]{1,32}$`), not against the active namespace (documented limit in `actions/README.md`; not a race, not tested).

### CW-4, CW-5, CW-6 (info)

- **CW-4.** `nemodots_admin` owns `checkout.config_entries` and can `DISABLE TRIGGER`; with the trigger off a forged marker is stored (test asserts it so the statement is exact). ARCHITECTURE 3 lists the admin URL as held by `stack.mjs`, `migrate.ts`, the test factory and the dev server process; keep it out of any process that handles model-derived input.
- **CW-5.** The ledger does not compare a registered `selfWrite` with the history; only the watcher derives it. Round 0 listed the `observe_source` executor as "not built"; it exists (`team/observer.ts`) and the call-site obligation is now checked: dynamically (the stored receipt of an executor call has `self_write = none`, `caused_by_action_id IS NULL`, `provenance_kind = tool_call`, even when the observed value itself contains `selfWrite` / `causedByActionId` fields, which stay plain content; a controlled member value with an extra marker field is refused by the ledger) and statically (the executor source never names `causedByActionId`, and `selfWrite` appears only on the line that forwards the stored provenance into the `receipt.registered` event). Future executors must keep to this.
- **CW-6.** `lease-boundary.test.ts`: a commit whose call began before the lease lapsed but reaches the row lock after it is refused (`DispatchFenceError`); a commit already holding the lock when the lease lapses completes, and the competing re-admission waits for the same lock and then returns `committed` without taking a new fence. Over 24 randomized A-commit / B-re-admit races around the expiry instant: never two commits, the commit Authorization's fence always equals the fence stored on the intent.

### CW-7 (medium) history squatting by the injector

Found by the round-1 reviewer on a surface round 0 listed as covered ("INSERT of `config_versions`" only proved that the marker is nulled).

- **Command.** `... vitest run --config tests/nemodots/adversarial/concurrency/vitest.config.ts self-write-forgery -t "history surface"`
- **Reproduction.** `nemodots_injector` holds a raw `INSERT` grant on `checkout.config_versions` (`0004_checkout.ts`). The triggers only null the marker; nothing ties a history row to the key's head. The injector inserts version 2 of `db.pool_max` while the head is version 1. The action admitted at expected version 1 then commits: `advanceConfig` computes version 2 and its own history insert hits `config_versions_pkey`.
- **Expected** (ARCHITECTURE 5.1 step 7): a failed compare-and-set surfaces as `blocked(stale_version)`; the authority is writable by its legitimate writers.
- **Actual.** The commit rejects with an untyped `23505` (`duplicate key value violates unique constraint "config_versions_pkey"`); the intent stays `admitted` and every retry fails the same way until it expires; the head stays at version 1 and no action row exists (**safety holds**); every later `advanceConfig` of that key (action, owner edit, injector) hits the same duplicate key, so the key is bricked. UPDATE and DELETE of history by the injector are refused (`42501`, passing test).
- **Tests.** `safety: with the successor version squatted...` passes (head unchanged, no action row, intent `admitted` or `blocked`). Three `it.fails`: **CW-7a** the commit is `blocked(stale_version)`; **CW-7b** the injector cannot insert a history row ahead of the head; **CW-7c** a later unconditional write still lands. Each was run as a plain `it` once and fails for the stated reason (23505, `expected 'ok' not to be 'ok'`, 23505).
- **Severity.** Medium: availability of the controlled authority can be destroyed by the fault-injector role, and a typed outcome the design requires is an untyped error. Not high: no write lands, no predicate is bypassed, and the role is the trusted fault injector.
- **Dependency (production).** (a) revoke direct `INSERT` on `checkout.config_versions` from `nemodots_injector`, or add a trigger requiring `NEW.version` to equal the key's head version written in the same transaction (fixes 7b and 7c, and 7a becomes unreachable); and/or (b) map `23505` on `config_versions` in `advanceConfig` / `commit.ts` to a `ConfigVersionError('stale_version')`, so the commit becomes `blocked(stale_version)` (fixes 7a only; the key stays bricked, so (a) is the real fix).

### CW-8 (low) a superseding registration starved by read-set writers

Found while making the executor property test deterministic (it failed in 2 of 6 whole-file runs with `ClosureUnstableError`).

- **Command.** `... vitest run --config tests/nemodots/adversarial/concurrency/vitest.config.ts c13-closure-unstable`
- **Mechanism.** `ledger/prelock.ts`: a registration previews the closure without locks, locks the coordinator rows of that closure, takes the ledger locks, re-reads the closure; a reader whose edge committed in between makes the round fail and the next round starts, at most `MAX_LOCK_ROUNDS = 6`, then `ClosureUnstableError` ("Nothing was written; the caller retries the whole step").
- **Deterministic reproduction.** Each round of the registration is held at its first coordinator row lock by a raw transaction that holds that attempt row; while it waits (observed by transaction id in `pg_locks`) one new reader commits its edge; releasing the holder lets the round find an unlocked attempt and fail; the next round blocks on the next holder. After 6 failed rounds the registration throws.
- **Expected.** Nothing lost; every caller that can supersede treats the error as a lost race.
- **Actual.** (a) Ledger: `ClosureUnstableError` (`code closure_unstable`), nothing written (head still revision 1 and supported, readers still `running`), a retry succeeds and marks all 7 readers: **holds** (liveness cost only). Watcher: the per-source guard reports one `error` event and a `failed` outcome, the next cycle registers revision 2: **self-heals**. (b) **CW-8b**: `observe_source`'s race loop (`team/observer.ts`) catches only `StaleObservationRejectedError`, `RevisionMismatchError` and `DigestMismatchError`; a starved registration of a _changed_ observed value leaves `observe()` as an untyped `ClosureUnstableError` instead of a retry or a typed `ToolError`. The tool call fails with an unclassified error and the attempt rests on the worker's generic failure path (`it.fails`).
- **Severity.** Low: liveness only, needs 6 consecutive reader waves on one receipt, nothing is written. Related: `ClosureCapExceeded` can also come out of the executor's registration (the C14 cap path exists only in the watcher); the cap (64 depth / 10 000 nodes) cannot be reached in a test without building a 65-deep chain and is not reproduced.
- **Dependency (production).** `team/observer.ts`: treat `ClosureUnstableError` like the other lost races (re-read and retry within `MAX_RACE_ATTEMPTS`, then the typed `source_unavailable`), and map `ClosureCapExceeded` to a typed tool error. Flip CW-8b to `it`.

## Freshness windows, in one place

- **Freshness at admission:** an observed premise is current if its receipt is not superseded and was confirmed within `maxAgeMs`; unregistered world changes are invisible; the commit can rest on a fact up to `maxAgeMs` + admission-to-commit latency old (CW-3), and longer while a superseding registration is starved (CW-8).
- **Freshness at dispatch:** only the `cache.namespace` version is re-checked, in the claim transaction; the claim-to-script window and the `redis.stats` age are not guarded (CW-3).

- The remaining `team/` executors (only `observe_source` is exercised here).

- Compensation (`compensate.ts`) racing a second action on the same key.
