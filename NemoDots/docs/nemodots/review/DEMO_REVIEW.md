# Demo and novelty review (W6.3 `demo-adversary`)

Reviewer: demo and novelty devil's advocate, a persistent subagent (no native team), model `claude-opus-5-5`. Date: 2026-10-18. Contract version: v1 (CONTRACTS revision 3). Source reviewed: HEAD `b3317ad` plus the uncommitted tree; `src/server/nemodots/**` digest `f8e95f2868c018de` (sha256 of the sorted per-file sha256 list); tests digest `c3af223a3d3e6e97`. No production file was edited. No live Crusoe mission was started by this review. `evals/nemodots/frozen/**` and `tests/nemodots/acceptance/**` were not read.

Evidence used: the code; the recorded live artifacts in `.local/dev/live/*.json` (Nemotron on Crusoe); the two recorded evaluation smoke trials in `evals/nemodots/results/{aa11a78b,ab04d9d9}*/trials.jsonl` (live); and new reproductions in `tests/nemodots/adversarial/demo/`. The dev database holds no mission rows. The live suites use throwaway `live-<rand>` instances, so live DB rows exist only as these exported summaries.

Reproductions labelled **[scripted]** use a scripted adapter policy. Everything is the real product: `createNemoDots`, the checkout API on its own port, the injector started through the product route, the watcher, ledger, coordinator, actions and the team code. The one exception is the model, which is a local Chat Completions server following a fixed policy (`scripted-mission.ts`). These runs prove plumbing, recovery and scheduling. They prove nothing about Nemotron's reasoning, and they are never live trials.

## 1. Verdict

The controlled-commit boundary and the provenance layer held under every check made here:

- A stale proposal was blocked.
- The ledger closure matched an independent traversal of the recorded edges.
- The independent branch was not re-run.
- Every output still usable at the end rested on current revisions.
- Nothing from the control plane, the scenarios or the oracle reached an agent, a receipt or the event stream.

The demonstration itself has not happened live, and three product defects stand in its way:

- **DA-02:** recovery never closes an invalidation after an aborted repair.
- **DA-05:** waiting parents starve their children of the two default worker slots.
- **DA-04:** acceptance runs while a repair waits for admission.

Delegation is real tool use, but prompts, plan rules, a closing-check nudge, refusal texts and a verifier policy induce it. The docs report only part of this. One runbook encodes a forbidden baseline value as a riddle (DA-01). The evaluation's "preserved work" number does not measure preservation (DA-03).

- **Team suite** (`team.json`, `team-trace.json`, action port stub): the planner chose 6 root tasks; investigator → specialist delegation; depth 2. 95 calls on Crusoe, at most 4 in flight. Proposals reached a stub, not the real boundary. Tool-call formatting errors (`invalid_arguments`, malformed `dependsOn`) were corrected by the model.
- **Evaluation smoke trial `aa11a78b`** (`cache_schema_mismatch`, selective): one verified `flush_cache_namespace`, then a fresh independent probe passed. The reference closure agreed with the ledger on 3 events. 143 calls, $0.248, 888 s.
- **Changed-evidence** (`mission-changed-evidence.json`, `live-fcd327`): the fault was observable; delegation reached depth 2; all 109 calls were on Crusoe. Everything else was NOT_MET or FAIL (section 4).
- **`worker-crash`** PASS; **`redis-loss`** PASS with reduced scope (no worker attached, so the effect-marker path was not exercised).
- **Browser E2E** (`docs/nemodots/E2E.md`): the page shows a proposal blocked `stale_version` after a manual source edit, then the invalidation and the scheduled recovery in event order. A seeder stands in for the model there; E2E.md says so.

Deterministic and scripted runs (not live):

- **[scripted] Branch A of the disjunction on the demo path:** `blocked(stale_version)` at admission, and a repair of the proposing task read the new revision. No commit landed on the superseded version.
- **[scripted] Selective preservation:** the independent routing branch made zero new attempts and zero model calls after the invalidation, in both the demo mission and the single-fault control.
- **[scripted] Leakage:** none of the forbidden vocabulary appears in the complete agent-visible corpus (every model request body), any receipt row, any mission event or the SSE stream. The forbidden set is scenario ids, classes, manifest and oracle field names, control tables, `injector`, the run id, the probe secret, `PROBE-SKU`, `caused_by` and `checkout.acceptance`.

## 3. What the demo does not show

- **The required qualitative demonstration, live** (BUILD_PROMPT `<testing_and_evaluation>`): an action derived from r1 rejected after r2 is registered, its worker re-reading, an independent branch not re-run, and the probe verifying the repair. It was never recorded with Nemotron. It exists only in deterministic integration tests and in the scripted reproduction here.
- **Autonomous delegation.** Six mechanisms induce it (section 5), and the depth-2 child is a mandated verifier. Its verdict is never read: `verifierConfirmed` checks only `succeeded` and `outputUsable` (`team/tools.ts:312-322`).
- **Open-ended diagnosis.** The runbooks pair each fault class's symptoms with its bounded repair:
  - schema back to the found version or flush (`cache-semantics.md`);
  - raise the pool (`pool-semantics.md`);
  - route to the authority, and set the write flag to the permitting value (`routing-semantics.md`).

  The planner reads the health error class directly. What the demo shows is Nemotron following an authorized runbook from an observed error class. BUILD_PROMPT allows this, but it is not discovery.

- **A comparison with the baselines.** NOT_RUN (EVALUATION.md section 10). Two smoke trials are not a rate.
- **Reliability.** Earlier prompt iterations failed the structural criteria about 1 run in 8 (W4.1). `healthy` passed 1 run in 9 before the metrics fix (W5.1 round 1). One of the two smoke trials resolved.
- **That fixtures are live.** No fixture was presented as live anywhere. But "Live" means only that an OpenAI-compatible endpoint is configured; see DA-14.

## 5. Does any prompt text mention delegation? Yes

All of these are model-visible. `leakage-static.test.ts` pins the list.

1. Planner (`team/prompts.ts:22`): "Include at least one investigator who owns the customer-visible failure end to end: it establishes the cause from readings and is responsible for getting it repaired by delegating to a specialist." It also says "include delegate for investigators".
2. Investigator (`prompts.ts:26-27`): "When your evidence points to a repair, delegate a narrowly scoped task to the specialist role…", and "Your task is not complete while a defect … is still unrepaired … delegate the repair to the matching specialist …, wait for the child, and report its outcome."
3. Specialist (`prompts.ts:44`): "ask a verifier (delegate_task, role verifier, then wait_for_children) to confirm your reading independently first."
4. Closing check (`worker-loop.ts:182-226`, `prompts.ts:63-67`): when an investigator reports a defect without having delegated, it is told "Delegate it now with delegate_task to the {area} specialist, … wait_for_children".
5. Refusals (`team/tools.ts`):
   - `capability_denied` for an investigator's proposal: "delegate the repair to a specialist with delegate_task and a justification";
   - `verification_required`: "before proposing a change, delegate a verifier (delegate_task with role verifier) …, wait_for_children, then propose". The recorded trace shows exactly this sequence after the refusal (`recorded-runs.test.ts`).
6. Plan validity rules (`planner.ts:84-101`): every investigator, and under the incident policy every specialist, must hold `delegate`, with one correction turn.

The planner may also create specialists as root tasks. In `team.json` one proposal path is `root>cache_specialist@0`, so a repair does not require an investigator.

## 7. Independent recomputations

- **Preserved set (D5).** For every invalidation event of the [scripted] demo mission and of the single-fault control, a breadth-first traversal from the old receipt over raw `ledger.dependency_edges` (evidence and inheritance edges that existed at the event's time) equals the product's per-mission affected set. For a verified self-write, the acting lineage is first removed, as ARCHITECTURE 5.4 specifies, using the receipt's `caused_by_action_id` and the task tree. The product's preserved set equals the existing tasks the traversal did not reach. Before applying the lineage rule my traversal reported 2 extra tasks per verified self-write. They are exactly the documented acting lineage (proposing specialist and its waiting investigator), not missed descendants.
- **Vectors at mission end.** Every output still `usable` at mission end has, for every vector entry, the latest `ledger.source_revisions` revision of its source at the mission's end time, in both [scripted] missions. In the recorded trials, no task counted as preserved rests on a receipt superseded by a recorded invalidation. One caveat: under the acting-lineage exemption, an output can stay usable over a superseded receipt by design. It did not happen in these runs, but it can.
- **Live test's set.** No recorded live run produced a non-empty set to compare (section 4).

## 9. Remaining risks and limits of this review

- After a fix, `checkout.metrics` mints a new revision once the error leaves its 30 s window (`METRICS_WINDOW_MS`). Every post-fix reader is then invalidated again. In [scripted] runs this re-invalidated 9 tasks about 30 s after the fix, and the extra repairs eat into `max_attempts`.
- A replan after a failed acceptance probe is told "Evidence changed since the earlier plan (see the invalidation summary)" (`team/replan.ts:56`), but it answers no invalidation event, so there is no summary. The probe result is model-invisible by design, so the planner replans without knowing why.
- A repair proposal can be blocked `missing_required_source: checkout.health` when the repair attempt did not re-read health. This is a policy block, and the scorer does not count it as a false block.
- Under the acting-lineage exemption, an output can stay usable while resting on a superseded receipt.
- The scripted policy is one fixed path. It cannot show how Nemotron's choices (replans that cancel tasks, flush instead of set) change DA-02, DA-04 and DA-09 in live runs.
- No live mission was run here, so none of the live findings is re-measured on the current tree. A live re-run is worth about $0.25 and 15 minutes only after DA-02 and DA-05 are fixed.
